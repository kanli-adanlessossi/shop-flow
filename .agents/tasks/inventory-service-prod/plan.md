## Decisions
- **Open point (order-platform tests vs token).** Use Spring Security's `OAuth2ClientHttpRequestInterceptor` with an `OAuth2AuthorizedClientManager` (client-credentials, registration `inventory`, client `shopflow-service`) on the inventory RestClient. The manager caches the token until shortly before expiry, so there is no token request per call. The registration uses an explicit `token-uri` (not `issuer-uri`), so the app still starts without Keycloak (same property as today for the resource server). No test bypass and no production toggle: the only contexts that call the real `InventoryClient` are the story tests (`StoryTestSupport`), which already start Keycloak; they get real tokens by pointing the registration's `token-uri` and `client-secret` at the Keycloak container in `KeycloakTestcontainersConfiguration`. Every other context mocks `StockReservations` or never calls inventory. A new test proves the Bearer header reaches the WireMock stand-in. WireMock stubs keep ignoring the header.
- **Compose.** Root `compose.yaml` holds `kafka`, `keycloak`, `postgres` (orders) and `postgres-inventory`. The two databases sit in compose profiles `orders` and `inventory` so Boot's service-connection detection in each app sees only its own PostgreSQL (two `postgres:` images would give two `JdbcConnectionDetails`). Each app sets `spring.docker.compose.file=../compose.yaml`, `lifecycle-management=start-only` (an app exiting never runs `compose stop` on infra the other app uses) and `profiles.active=<own>`. Kafka and Keycloak have no profile and always start. Ports unchanged: Keycloak 8180, Kafka 9092. Inventory DB: named volume `inventory-db-data`, fixed host port 5433. `order-platform/compose.yaml` and `inventory-service/compose.yaml` are deleted. If Boot with profiles does not behave as assumed (verify in FEAT-001 with `docker compose --profile orders config` and by running both apps in FEAT-003/e2e), fall back to the same file with `spring.datasource.url` set explicitly per app, not to separate files.
- **Event contract.** `OrderConfirmed` gets a nullable `reservationId` (optional field; old messages still read). New `OrderShipped(long orderId, String reservationId)` with `@JsonTypeName("order.shipped")`, key = orderId, written to the outbox in `OrderService.updateStatus` on CONFIRMED -> SHIPPED. order-platform's `OrderEventHandler` skips `OrderShipped` before the inbox mark (no notification, no new behaviour); `LoggingNotificationSender`'s sealed switch needs an `OrderShipped` case that throws like `UnknownPayload` (it is never reached).
- **Inventory reservation semantics.** Rows: `stock(sku pk, available >= 0)`, `reservation(reservation_id pk, status HELD|CONFIRMED|SHIPPED, created_at, updated_at)`, `reservation_line(reservation_id, sku, quantity)`. Reserve in one transaction: `insert ... on conflict do nothing` on the reservation id (0 rows = retry, answer 200 with no further change); merge duplicate SKUs in the request; then per SKU in sorted order `update stock set available = available - :q where sku = :sku and available >= :q` (0 rows or unknown SKU -> `InsufficientStockException` -> rollback -> 409). Release: HELD/CONFIRMED -> add quantities back and delete the reservation (204); SHIPPED -> 409; absent -> 404. Transitions only move forward (HELD -> CONFIRMED -> SHIPPED); confirm/ship of an unknown reservation or an event without reservationId is logged and skipped (never thrown, so no DLT); confirm of an already CONFIRMED/SHIPPED one is a no-op; ship from HELD is allowed so a reordered retry cannot get stuck.
- **Expiry.** `shopflow.inventory.hold-ttl` default `45m` (> order-platform's 30m cancel-after), job cron every 5 minutes, ShedLock `expireHeldReservations`, each reservation released in its own transaction through the same release path. CONFIRMED never expires.
- **Realm.** Add realm role `inventory` and grant it to `service-account-shopflow-service` (keep `admin`).
- **Inventory tests share ONE Spring context** (abstract base with Postgres + Kafka + Keycloak containers, identical properties, no per-class `@MockitoBean`), like `StoryTestSupport`, to respect the CI target. The one extra context is the `@DataJpaTest` slice with its own Postgres.
