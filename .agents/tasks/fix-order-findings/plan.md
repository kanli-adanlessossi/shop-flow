## Design decisions (made here, record them in the final summary)

**C1: where prices come from.** The repo has no price source. `inventory-service` is an empty skeleton and `StockLevel` is `(sku, available)` only. Decision: a local price table `sku_prices(sku pk, unit_price numeric(12,2))` in order-platform's own database, read by `OrderService` when it builds order lines.
- The client-supplied `unitPrice` is removed from `OrderLineRequest` for everyone, admins included. One rule is easier to reason about than "admin may override", and no story needs an admin override. A body that still carries `unitPrice` is ignored (Boot's Jackson setting does not fail on unknown properties; the coder confirms this with the client-price test).
- Unknown SKU: new `UnknownSkuException`, HTTP 422 problem detail, thrown before stock is reserved so nothing leaks.
- `replace` re-prices from the table as well. Stored `order_lines.unit_price` stays a snapshot, so later price changes do not alter existing orders and `confirmPayment` still compares against the stored total.
- Price rows are maintained by SQL/migration. No admin endpoint is added (out of scope). Dev profile gets seed rows for the SKUs the load test uses (`SKU-001`..`SKU-008`), tests get seed rows through a Flyway callback in test resources.
- Alternatives rejected: inventory-supplied prices (the contract is invented and the service does not exist); admin-only client prices (still needs a source for customers).

**C2: transition rule.** `PATCH /api/orders/{id}/status` becomes ADMIN only (`STATUS_RULE = ADMIN`). The owner's only legitimate status change is cancel, which is already admin-only (US-9), so the owner branch was pure bypass. Allowed through PATCH: `PENDING_PAYMENT -> CANCELLED` and `CONFIRMED -> SHIPPED`. Everything else is a new `IllegalStatusTransitionException` mapped to 409. Same status as current is a no-op that returns the order (US-9 says cancelling twice answers 200 and emits one event). `CONFIRMED` is reachable only through `confirmPayment`; the cleanup job keeps cancelling through `cancelIfStillUnpaid`. `CONFIRMED -> CANCELLED` is now rejected: no refund path exists (review L13), and the review's fix lists only the two transitions. Name this as a behavior change.

**H1: release.** Release the reservation after commit, via `ReservationRelease.releaseInBackground`, registered with `TransactionSynchronizationManager` (afterCommit) inside the `@Transactional` methods. A direct call inside the transaction could release stock for an order whose transaction then rolls back (H2 conflict). `delete` releases for both PENDING_PAYMENT and CANCELLED orders (release is idempotent, and it heals reservations leaked by earlier deletes). Admin cancel releases (only possible from PENDING_PAYMENT now).

**H2: concurrency control.** Optimistic locking: `@Version long version` on `Order`, Flyway `V8`. Reason: contention per order is rare, no lock is held across the remote calls, and it works the same on H2 and PostgreSQL. A lost race becomes `ObjectOptimisticLockingFailureException`, mapped to 409 (`ApiExceptionHandler`). A webhook that loses the race rolls back its inbox row and outbox event, so the provider's retry is handled fresh (and then gets `ALREADY_CONFIRMED` or `LatePayment`). The cleanup job already catches `RuntimeException` per order, logs and counts it skipped. No retry loop is added. The M2 window (release before cancel) is not touched.

**H3: list scoping.** `OrderService.search(@Nullable String customerId, @Nullable OrderStatus status, Pageable)`. The controller passes `null` for admins (`ROLE_ADMIN` in `authentication.getAuthorities()`) and `authentication.getName()` for everyone else. Four list queries instead of two (`findSummariesByCustomerId`, `findSummariesByCustomerIdAndStatus` plus their count queries), not a `:customerId is null or ...` condition, to avoid the PostgreSQL untyped-null-parameter problem. No `customerId` filter parameter for admins (not asked).
